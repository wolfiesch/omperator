# ADR-020: Omperator owns the settings information architecture; the bridge exposes two generic config seams

- Status: proposed. Supersedes nothing; extends ADR-003 (app-wire v1) and ADR-013 (t4-host ownership). Full analysis in [`../SETTINGS_SURFACE_SPEC.md`](../SETTINGS_SURFACE_SPEC.md).
- Context: the settings workspace derives its sections directly from OMP's `ui.tab` metadata (`apps/web/src/features/settings/live-catalog.ts:437`). The pinned fork's schema declares a tab for 309 of its 421 keys, so 112 keys fall into a single unlabelled Advanced bucket today, rising to 116 of 439 once the runtime pin catches up to upstream. Those keys are not obscure: they include `modelRoles`, `cycleOrder`, `enabledModels`, `disabledProviders`, `thinkingBudgets.*`, `statusLine.*Segments`, `task.disabledAgents`, and every `skills.*` discovery toggle. The 54 section headings OMP declares in `TAB_GROUPS` are consumed as a sort key and never rendered. Twelve of the 22 rail section ids in `SettingsWorkspace.tsx:58-79` reference tabs OMP does not publish, so those entries never render and the Integrations group never appears at all. The untabbed keys are untabbed for a terminal-specific reason: the schema's own `UiNumber` and `UiArray` comments state that numbers and arrays without submenu options have "no UI representation" because a terminal cannot render them. Inheriting a terminal's rendering constraints into a desktop app is the root defect.
- Decision 1 (IA ownership): Omperator owns the settings information architecture. A checked-in manifest, `docs/settings-surface/coverage.json`, partitions the setting-path space across six groups, 31 rail entries, and 80 named sections, following the shape of a turn: Agent, Tools, Context, Session, Interface, System. Depth lives in in-page sections rather than in more rail entries, which is what lets a 40-key page read as five short lists and keeps the rail scannable. OMP's `tab` and `group` remain useful hints for ordering and for labelling unrecognized keys, but they no longer determine navigation. The Advanced dumping ground is deleted.
- Decision 2 (coverage is enforced, not aspirational): claims are made at page-section granularity, so one manifest drives the rail, the page body, and the section headings. Resolution is two-tier and must be unambiguous. A section claims keys by `exact` list or by `prefixes`; exact claims win; more than one claim at either tier is an error, and zero claims is an error. First-match-wins prefix ordering is rejected because a broad prefix can silently shadow a narrower one and the shadowing is invisible in review. Prefixes are authoring shorthand for a namespace that genuinely belongs in one section, never a catch-all: the generator expands every claim against the pinned schema and commits the resulting `keys` arrays, so the CI check is "regenerate and the diff must be empty" and a new upstream key always surfaces as a reviewable diff naming its landing section. No section may exist to absorb unclaimed keys, and a section whose expansion is empty fails the check, because a claim owning nothing is a catch-all in waiting. `scripts/check-settings-coverage.mjs` runs in `pnpm check`. A runtime key from a mismatched host still renders, inside a per-page "unrecognized" affordance and recorded in `issues[]`; that is a host diagnostic, not a substitute for curation. The check earned its place before any UI existed: it caught four overlapping `hindsight.mentalModel*` claims, and it forced the removal of two zero-key catch-all sections, while this IA was being cut.
- Decision 3 (two generic bridge seams, not nine domain APIs): file-backed OMP configuration (MCP servers, skills, agents, commands, rules, instruction files, themes, keybindings, custom model providers, hooks, custom tools) is exposed through one CRUD family, `config.resource.list|read|write|delete`, keyed by a closed `kind` enum plus a `scope` of `user` or `project`. Imperative configuration operations (provider login and logout, MCP test and reauth, plugin and marketplace lifecycle, memory maintenance, profile create and switch, settings reset) are exposed through one family, `config.action.invoke`, keyed by a closed action enum. Nine bespoke domain APIs would be nine independent chances to diverge on revision guarding, containment, and error shape.
- Security boundary for `config.resource.*`: the wire carries `kind` plus `scope` plus an opaque stable id, never a filesystem path, root, or directory. The OMP-side authority resolves `kind` and `scope` to an allowed base directory, canonicalizes the candidate, and enforces containment before any read or write; symlink escape and ids that normalize outside the base are rejected. The host authenticates the IPC sender and derives host and project ownership server-side, matching the posture the session channels already use; no renderer-supplied identifier is trusted for authorization. Writes are revision-guarded, size-bounded, and atomic, with the rollback discipline `DesktopConfigAuthority.#settingsWriteNow` already applies to settings. Resources discovered from foreign providers (`.claude`, `.codex`, `.gemini`) and bundled built-ins are returned `readOnly` and are copied rather than edited in place.
- Decision 4 (secret classification is declared, not inferred): `desktop-config-authority/authority.ts:27` classifies a setting as sensitive when any path segment matches a substring regex containing `token`, `secret`, and `auth`. Applied without word boundaries this censors and blocks writes to 22 keys, 13 of which are innocuous, including `display.showTokenUsage`, `share.redactSecrets`, `secrets.enabled`, and every `…Tokens` numeric budget under `compaction.*`, `memories.*`, `hindsight.*`, and `commit.*`. The regex is replaced by an explicit allow-list derived from the schema's `ui.secret` flag plus a reviewed additions list. Sensitive values are still never sent to the renderer; a `secretStatus` (set, unset, from-env, from-broker) is sent instead, and a dedicated write-only editor sets, rotates, and clears them. Widening the writable set is reviewed as a security change, not a UI change.
- Runtime pin consequence: the settings universe the GUI can render is the pinned fork's schema, not upstream's, and the two disagree on 34 keys. The fork declares 421 against upstream's 439, a net deficit of 18 that understates an asymmetric drift of 26 missing plus 8 extra. Missing: all five `computer.*`, `bash.patterns`, `bash.direnv`, `bash.direnvLoadTimeoutMs`, `error.notify`, four `hindsight.*` timeouts, `mcp.renderMarkdownResults`, `providers.imageOrder`, `providers.webSearchOrder`, `read.renderMarkdown`, three `retry.usage*` keys, `searxng.engines`, `task.isolation.apply`, `tools.xdevDocs`, `tools.xdevInlineDevices`, `tui.titleState`, and `workspace.additionalDirectories`. Extra: four `appserver.remote*` keys, `task.maxNestedConcurrency`, `task.nestedEager`, and the upstream-removed legacy `providers.image` and `providers.webSearch` enums. The coverage manifest is generated over the union of both schemas so a pin bump does not break it, and CI reports both directions of the drift on every run rather than a single net number that hides the extras.
- Upstreamability: the schema needs `min`, `max`, `unit`, and `restartRequired`, which `authority.ts:183-194` already forwards but `settings-schema.ts` never declares (zero occurrences of each). These are useful to `can1357/oh-my-pi` independent of Omperator and are offered upstream rather than carried as fork debt. The information architecture, the coverage manifest, the route map, and both bridge seams are Omperator's and stay in the fork or in Omperator.
- Client scope: `apps/mobile` packages the web bundle and inherits the whole surface. `apps/ios` is a native Swift client that does not mount the settings workspace and is unaffected; a Swift settings surface is out of scope and is recorded as such in the parity ledger.
- Verification: coverage and drift checks in `pnpm check`; a test asserting no key in the pinned schema resolves to the unsupported-control fallback; containment tests for `..`, absolute paths, symlinks, and foreign-scope ids on every resource kind; Playwright specs that edit one key per control kind and one resource per kind and assert the resulting on-disk file; a parity ledger test that fails when a new built-in slash command, catalog kind, or resource kind appears with no entry.
